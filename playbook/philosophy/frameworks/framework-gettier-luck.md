# Framework — Gettier Luck (True-by-Accident)

## 1-sentence thesis
A belief can be **true and justified** yet still fail to be knowledge if it is true **by luck** rather than by a reliable connection to reality.

---

## Model (Operational)
### Three conditions people confuse
1) **Truth:** the statement matches reality  
2) **Justification:** there are reasons given  
3) **Non-luck / Tracking:** the reasons connect to reality in the right way

Gettier cases show:
- You can hit the correct answer while the reasoning path is fragile.

---

## When to use
Use this framework when:
- a student gets 5/5 but the “why” is vague
- AI outputs are correct but unverifiable
- a system looks good until conditions change (time pressure / trap density)

---

## Failure modes
- **FM1: Mistaking correctness for stability**  
  “If it’s correct today, it’s safe tomorrow.”
- **FM2: Over-trusting one success**  
  “It worked once, so the method is reliable.”
- **FM3: Ignoring pressure tests**  
  “No need for timed sets because accuracy is high.”

---

## Bridge-to-Lab (Reading Judgment)
This framework justifies why we track **evidence artifacts** even on perfect-score days.

- Perfect score can still be **True-by-luck** if evidence discipline is missing.
- Risk codes exist to detect this early.

Example link:
- `R-COMFORT-1` triggers pressure testing even when there is no active error.

**Operational rule:**  
High accuracy without pressure testing is not proof of stability.
